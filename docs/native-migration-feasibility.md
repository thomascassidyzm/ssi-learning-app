## Executive summary

**This is feasible, it is the right move, and it is genuinely "better × simpler × cheaper" — collapsing two codebases into one while keeping the working app-store funnel intact.** The wrap is not a rewrite: the Vite build already emits a clean static `dist/` (confirmed: `vercel.json` → `packages/player-vue/dist`), which is exactly what Capacitor's `webDir` consumes. Auth survives untouched (confirmed: `verifyOtp` uses a **numeric 6-digit code**, not a magic link — so zero deep-link interception is needed, the classic Capacitor auth headache simply doesn't apply here). Offline audio is in IndexedDB (`ssi-audio-cache-v2` + mp3→WAV decode), independent of the service worker, so losing the SW inside WKWebView costs nothing load-bearing. And the funnel attaches to the **bundle ID**, not the framework — shipping the Capacitor build as an in-place update under the same App Store Connect / Play listing preserves reviews, ranking, and the running paid-install campaigns. A framework swap is invisible to the funnel.

**There are exactly two real lumps, and they are both engineering, not policy or mechanics:**

1. **Native payment + IAP-continuity (the dominant lump).** The current £15/mo checkout is a Paddle web redirect (`useSubscription.ts:235` `window.location.href = data.checkoutUrl`). Apple will not accept that as the in-app purchase path; the wrap needs a native IAP layer. There is **zero RevenueCat/StoreKit/Play-Billing code in the repo today** — this is net-new. The good news that makes it tractable: `useSubscription` is already provider-agnostic by design (its own comment: "easy provider swap … by only changing API endpoints"), the `subscriptions` table is already `UNIQUE(learner_id)` with a `provider` column, and the Paddle webhook already hard-links payment to identity. RevenueCat slots into this shape cleanly and (crucially) shipped a native **Paddle Billing integration in 2025**, so the dual IAP+web reality can collapse into ONE entitlement.

2. **iOS locked/background audio in WKWebView (the high-uncertainty lump).** WKWebView *is* WebKit — the exact battle the team fought on the PWA recurs identically, and `CLAUDE.md` documents it as "learnt twice" (the oscillator-keepalive in `useAudioSessionKeepalive.ts` is the only thing that works, 30+ min locked). The wrap is **no worse** than the PWA (same engine) and, for the first time, offers a real escape hatch: a native `AVAudioSession` held by app-process Swift. But whether the team needs that escape hatch is **the single highest-leverage unknown in the whole project**, and it must be settled by a real-device spike in week 1, before anything else is built.

Everything else — the wrap mechanics, the cutover sequencing, the store policy, the identity spine — is well-understood, low-to-moderate effort, and reuses machinery that already exists. Porting capacity (3× Pro Max) is not the constraint; the constraint is getting these two lumps right and the slow, one-directional store-review clock.

**Realistic end-to-end to a same-bundle-id store replacement: ~6–10 weeks of focused work**, front-loaded by the audio spike and the payment rail, gated by Apple/Play review turnarounds rather than coding throughput.

## How the pillars fit together (the cross-dependencies that matter)

The seven pillars are not independent — three threads run through all of them, and resolving them once resolves them everywhere:

**Thread 1 — RevenueCat is the keystone that ties payment, identity, and continuity into one decision.** The IAP pillar, the identity-spine pillar, the continuity pillar, and the economics pillar all independently land on the same answer: adopt RevenueCat with `appUserID = the SSi-ID (learners.id)`. That single choice does five jobs at once:
- It is the native IAP rail Apple requires (wraps StoreKit2 + Play Billing).
- Its `appUserID` IS the IAP-continuity key — set it to the stable Supabase `user_id` and existing payers resolve to one customer; a first-launch `syncPurchases()` (silent, no OS prompt) pulls the existing Apple receipt / Google purchase into RevenueCat so existing payers light up with no action.
- Its `appUserID` IS the identity-spine's billing hard-link — RevenueCat sets `appAccountToken` (Apple) and `obfuscatedAccountId` (Google) for you, so a native payer is resolvable from a transaction, exactly as the Paddle webhook already resolves web payers via `customData.supabase_user_id`.
- Its native Paddle-Billing integration unifies web + IAP into one entitlement, matching the existing `subscriptions` table's `UNIQUE(learner_id)` single-source-of-truth.
- The entitlement READ path (`useEntitlement` → `useSubscription` → `/api/subscription`, confirmed) is unchanged; only the WRITE/checkout path forks on `Capacitor.isNativePlatform()`.

So "the IAP work" and "the identity work" and "the continuity work" are largely **one workstream**, not three. This is the biggest simplification the synthesis surfaces.

**Thread 2 — native audio is simultaneously an audio-pillar item AND a parity item AND a 4.2-approval lever.** The same `UIBackgroundModes:audio` + `AVAudioSession` work that the audio pillar treats as the lock-screen fix is, to the parity pillar, the thing that turns the oscillator-hack into a real entitlement, and to the policy pillar, one of the native behaviours that clears App Store Guideline 4.2 "minimum functionality". One plugin, three wins. The pillars agree the native layer should **hold the session + own lock-screen controls**, while the Vue engine keeps 100% of playback orchestration (the adaptive `pauseTimer`, spaced-rep, spike detection stay in `@ssi/core` TS). Native *playback* (deleting the WAV-decode hack) is a tempting phase-2 simplification but a phase-1 trap — it would re-implement the learning engine across a JS/native boundary, the exact rewrite this whole strategy exists to avoid.

**Thread 3 — the anonymous-account gap is the quiet prerequisite for IAP continuity.** Today a guest is a `guest-<uuid>` in localStorage (confirmed `useAuth.ts:65`) that is *deliberately excluded* from every DB write. A payer who pays as a guest and reinstalls is unrecoverable. The identity-spine pillar's fix — replace the localStorage hack with Supabase anonymous sign-in so the SSi-ID is server-persisted from first launch — is what guarantees the `appAccountToken` always has something to point at *before* a purchase is initiated (StoreKit reads it at purchase init; it cannot be set retroactively client-side). So the identity work isn't cosmetic; it removes a footgun on the critical payment path.

**Where the pillars conflict or hedge — read these honestly:**
- The audio pillar says the wrap "gives the first real fix"; the cutover pillar warns the wrap could *regress* vs Flutter (a pre-rendered long file survives lock trivially once playing). **Both are right and they don't actually conflict:** the wrap is no worse than the *PWA*, but the bar to beat is the *Flutter* app, which may clear lock-screen playback effortlessly precisely because it's a dumb long file. This is why the week-1 spike must measure against the Flutter baseline on a real device, not against the PWA.
- The economics pillar says "keep IAP, 15% is survivable, the US 0% external-link window is a bonus not a plan"; the policy/mechanics pillars note external-link is *possible* post-Epic. Resolved: **keep IAP as primary** (it powers the 3-5% conversion), add a US-only external Paddle link behind a server-side flag as an additive experiment — never ship the iOS app with IAP removed.

## Background / lock-screen audio via native plugin (Capacitor WebView wrap of player-vue)  —  _caveated_

A Capacitor wrap does NOT make the iOS background-audio problem disappear — and importantly it does not make it worse either. WKWebView runs its HTML5 `<audio>` in a separate GPU/media process with its OWN AVAudioSession that the host app cannot directly set, so the exact failure they already fought on PWA (audio dies ~15s after lock with a "Background task expired while holding WebKit ProcessAssertion" error) recurs identically inside Capacitor. The good news: their existing AudioContext-oscillator keepalive (useAudioSessionKeepalive.ts) is precisely the web-side mitigation that has been verified working 30+ min locked, and a native plugin gives a STRONGER, app-process-level version of that same trick (a real AVAudioSession.setCategory(.playback) held by native Swift code). The clean, cheap design is: native plugin HOLDS the session alive + owns the lock-screen controls; the existing Vue engine KEEPS doing all playback orchestration. The off-the-shelf plugins (capacitor-community/native-audio, mediagrid/capacitor-native-audio) are built for "play one long track / radio stream" and cannot drive the timer-orchestrated, sub-second, 4-phase adaptive cycle — so this needs a thin CUSTOM plugin, not a drop-in. This is a real, bounded engineering project (the highest-risk pillar), not a clean freebie, but it is the FIRST environment where a true fix is even possible, and it can finally retire the WAV-from-IndexedDB decode hack.

**Key findings**
- **The iOS root cause is architectural and survives the Capacitor wrap unchanged** — WKWebView's media plays in a separate process with its own AVAudioSession; the app's AVAudioSession category (even .playback + mixWithOthers) is ignored by WKWebView (Apple Forums 24464, WebKit bug 167788/173932). So merely wrapping player-vue in Capacitor and adding UIBackgroundModes:audio does NOT reliably keep HTML5 <audio> alive when locked — multiple reports confirm ~15s death with 'Background task expired while holding WebKit ProcessAssertion' (Capacitor discussion #3446). The PWA fight and the naive-Capacitor fight are the SAME fight.
- **Their existing oscillator keepalive is the correct mental model — and a native plugin is the upgraded version of it** — useAudioSessionKeepalive.ts runs a session-wide AudioContext + silent 0Hz/0-gain oscillator that 'sits one layer below the <audio> element, holding the iOS session without competing for the slot' — verified working 30+ min locked per CLAUDE.md. A native plugin replaces this in-web hack with a real app-process AVAudioSession.setCategory(.playback) + (if needed) a silent native AVAudioPlayer loop. This is the SAME principle (hold the session, don't fight for the slot) but at the app process level where it is far more robust against the ProcessAssertion expiry. Design answer to the brief's key question: the native layer should HOLD THE SESSION ALIVE + own lock-screen controls; it does NOT need to take over playback.
- **Off-the-shelf audio plugins do NOT fit the atomic-cycle engine — a custom plugin is required** — capacitor-community/native-audio and mediagrid/capacitor-native-audio are designed for continuous single tracks / radio streams (play/pause/seek, onAudioEnd, getCurrentTime). The mediagrid README explicitly lacks queue/low-gap-sequential-clip support. SSi's loop is timer-orchestrated in TS: SimplePlayer's pauseTimer owns phase advance (not audio-ended), pause duration is ADAPTIVE (computePauseDuration.ts + AdaptationEngine, 2x target length, spike detection), and clips are sub-second per-phrase (~25KB). Handing that to a track-oriented native player would mean re-implementing the 4-phase state machine, spaced-rep, and adaptation natively — a rewrite, which violates the one-codebase premise. Hence: thin custom plugin (session + MediaSession bridge), web keeps orchestrating.
- **If they go further to native PLAYBACK, the WAV-from-IndexedDB hack disappears — a genuine simplification** — wav.ts + AudioCache.getWavBlobUrl decode mp3→16-bit WAV per clip purely because WebKit's <audio> refuses mp3 blob: URLs from IndexedDB ('operation is not supported'). A native AVAudioPlayer/AVAudioEngine plays mp3 bytes directly — so a native-playback variant would delete the entire decode-and-re-encode path. That is the 'better x simpler' upside, but it costs 'simpler' elsewhere: the phase timing, gapless scheduling and adaptive pause would need a clean JS↔native command protocol. Recommend session-hold-only FIRST; native-playback is a possible phase 2 only if session-hold proves insufficient.
- **Android is the well-trodden, lower-risk half** — Android kills WebView audio when backgrounded too, but the standard fix is mature: a foreground service of type mediaPlayback + MediaSession + a media-style notification (FOREGROUND_SERVICE / FOREGROUND_SERVICE_MEDIA_PLAYBACK / WAKE_LOCK perms). jofr/capacitor-media-session and mediagrid/capacitor-native-audio both implement this; jofr explicitly starts a foreground service for active media sessions and you wire the <audio> element to it manually. This maps cleanly onto their already-wired MediaSession code (LearningPlayer.vue setupMediaSession + SimplePlayer.updateMediaPositionState).
- **Their MediaSession + position-state plumbing is already built and portable** — LearningPlayer.vue:4263-4313 already sets MediaMetadata, play/pause/nexttrack(skipRound)/previoustrack handlers, and playbackState. SimplePlayer.updateMediaPositionState (line 246) already feeds setPositionState every timeupdate specifically to stop Android suspending the tab. A native plugin's MediaSession bridge slots into these exact call sites — low re-plumbing cost. Minor gap: there is NO playsInline attribute set anywhere in src (grep clean), which matters for the WKWebView/inline path; trivial to add.

**Risks**
- _(high)_ Session-hold-only native plugin still relies on WKWebView keeping its media process alive; if Apple's ProcessAssertion expiry fires regardless of an app-level AVAudioSession, web-audio still dies locked and you're forced into the much costlier native-playback path → De-risk in week 1 with a throwaway spike: bare Capacitor wrap + UIBackgroundModes:audio + a 5-line Swift AVAudioSession.setCategory(.playback,.mixWithOthers)+setActive at app launch, play their cached clips locked for 30+ min on a real iPhone (iOS 17/18). This single experiment decides session-hold-only vs native-playback BEFORE committing. Confirm against current iOS — most cited failures are iOS 13-era and behaviour has shifted across versions.
- _(medium)_ The Flutter app's current background behaviour (the bar to beat) is unknown from this machine — you could ship something no better than today → Confirm against the Flutter repo / a test device: does the current native app actually play locked/backgrounded robustly (pre-rendered long files trivially survive lock once playing)? If Flutter's pre-rendered file plays fine locked, the Capacitor target must MATCH that bar, which raises the pressure toward native-playback. Flag as must-confirm.
- _(high)_ Choosing native PLAYBACK (not just session-hold) silently re-implements the learning engine across a JS/native boundary → Treat native-playback as a separate, explicitly-scoped phase-2 decision, never the default. The adaptive pauseTimer, spaced-rep and spike-detection MUST stay in @ssi/core TS; if native ever plays clips, it must be a dumb 'play this clip now, tell me when ended' slave to the existing state machine, with timing still owned by JS. Anything more is the rewrite the whole strategy exists to avoid.
- _(medium)_ App Review rejection for a backgrounded silent-keepalive that does nothing audible (Apple has rejected apps whose only 'audio' is a silent keepalive) → Because real learning audio IS sounding during a session, the UIBackgroundModes:audio declaration is legitimately justified — this is a genuine audio-playback app, not a keepalive-to-stay-alive abuse. Keep any silent loop strictly as a same-session gap-filler tied to active playback, never a standalone background daemon. Document the audio justification in review notes.
- _(low)_ Maintenance/abandonment risk of community plugins for load-bearing logic → Prefer a small in-house custom plugin (Swift+Kotlin, ~a few hundred LOC each) over depending on community plugins for the load-bearing session/MediaSession logic — they have known maintenance gaps (cordova-plugin-background-mode reported dead). The custom surface stays small because the engine stays in JS.

**Recommendations**
- Run the de-risking spike FIRST (1-2 days): bare Capacitor + iOS Background Modes:audio + native AVAudioSession.setCategory(.playback) at launch, then play cached clips with the existing engine on a locked real iPhone for 30+ min. This binary result drives everything downstream.
- If the spike passes (web audio survives locked once the app owns AVAudioSession): build a THIN custom Capacitor plugin that only (a) sets/holds AVAudioSession on iOS, (b) runs an Android mediaPlayback foreground service + MediaSession, (c) bridges the already-wired MediaSession handlers. The Vue engine keeps 100% of playback orchestration. This is the better x simpler x cheaper path.
- Retire useAudioSessionKeepalive's oscillator ONLY on native builds (keep it for the PWA build via a Capacitor platform check) — the native session-hold supersedes it on iOS, but the PWA still needs the oscillator. One codebase, platform-gated keepalive.
- Keep the WAV-from-IndexedDB decode (wav.ts) for now — it is web-audio-specific and only worth deleting if you later move to native PLAYBACK, which should not be phase 1. Do not entangle the two decisions.
- Add playsInline / webkit-playsinline to the audio/video element handling before any device testing — it is currently absent in src and is a known WKWebView gotcha.
- Confirm the Flutter app's actual locked-playback behaviour on a device to set the real bar to beat, and reuse the existing LearningPlayer MediaSession + SimplePlayer.updateMediaPositionState call sites as the native bridge integration points.

**Effort:** Spike to decide the path: 1-2 engineer-days on a real iPhone. If session-hold-only works (likely on current iOS): thin custom plugin iOS+Android ~1-1.5 weeks incl. App-Review-safe background config + device soak. If forced to native PLAYBACK: 3-5+ weeks and architecturally invasive — gate hard behind the spike. Sequence: spike → iOS session-hold plugin → Android foreground service → multi-version device soak (iOS 17/18, Android 13/14).

## IAP subscriber continuity through the Flutter→Capacitor binary swap  —  _caveated_

Swapping the Flutter binary for a Capacitor wrap under the same bundle/package ID does NOT touch the underlying StoreKit/Play Billing subscription records — the store, not the app, owns the subscription. So existing Apple/Google payers keep paying regardless of which binary is installed; the only real question is whether the NEW app can SEE that they are entitled. The clean continuity path is RevenueCat with a CLIENT-SIDE migration: on first launch of the Capacitor build, call syncPurchases() (silent, reads the local Apple receipt / queries the active Play purchase, no OS prompt, no sign-in) so RevenueCat picks up the existing originalTransactionId / purchaseToken and unlocks entitlement. Crucially, RevenueCat shipped a native Paddle Billing integration in 2025, so the existing Paddle web subscriptions can sync into the SAME RevenueCat entitlement state — the dual IAP+web reality collapses into one unified entitlement, which maps cleanly onto the existing single-row-per-learner subscriptions table. The genuine risks are all in the details: the StoreKit2 In-App Purchase Key MUST be configured in RevenueCat or transactions silently fail to record (the classic orphaning bug); a learner who paid via Paddle then appears via IAP (or vice versa) needs deliberate identity-linking or you double-charge; and three facts are UNKNOWN until the Flutter repo is read — which IAP plugin/product IDs it uses, whether RevenueCat is ALREADY integrated, and whether they store receipts server-side. Confirm those three and this is a low-drama swap.

**Key findings**
- **The subscription lives in the store, not the binary — same bundle ID = automatic billing continuity** — An auto-renewable subscription on Apple is tied to the Apple ID + app's bundle ID; on Google to the Google account + package name. Replacing the Flutter .ipa/.aab with a Capacitor build under the SAME identifiers does not cancel, pause, or alter any subscription — Apple/Google keep charging on schedule. No payer is 'orphaned' at the billing layer by the swap itself. The ONLY work is making the new app recognise the existing entitlement on first launch.
- **Client-side RevenueCat migration is the right path: syncPurchases() on first launch, silently** — RevenueCat docs: for users who already have the app installed with an existing subscription, syncPurchases() 'reads the existing local receipt and sends it to RevenueCat for validation without triggering any OS prompts.' This is the key difference from restorePurchases(), which refreshes the receipt from Apple and CAN trigger a sign-in prompt. So the Capacitor build calls Purchases.syncPurchases() once when it detects a user who isn't yet known to RevenueCat — the existing originalTransactionId (Apple) / purchaseToken (Google) flows in, entitlement unlocks, no learner action required. RevenueCat warns NOT to call this on every launch for every user (latency + can merge profiles) — gate it to a one-time post-migration sync.
- **RevenueCat NATIVELY integrates Paddle (2025) — the dual IAP+web reality can become ONE entitlement** — RevenueCat launched a Paddle Billing web-payment integration in open beta April 9 2025, GA-announced June 2025. It supports external purchase syncing AND embedded checkout. This is unusually lucky for SSi: their web payer is already Paddle (api/_utils/paddle.ts, lib/paddle.ts), so the existing Paddle subscriptions can be wired into RevenueCat and surface in the same cross-platform entitlement that IAP feeds. A learner is 'Premium' if EITHER source is active — exactly the single-source-of-truth the current subscriptions table already assumes.
- **The existing subscriptions schema already models this correctly — one row per learner, provider-tagged** — /Users/tomcassidy/SSi/ssi-learning-app/supabase/migrations/20260418_subscriptions.sql defines subscriptions with UNIQUE(learner_id), a provider TEXT column, provider_subscription_id, provider_customer_id. The Paddle webhook (api/teacher/paddle-webhook.ts) upserts with onConflict:'learner_id', provider:'paddle'. The app reads ONE row via api/subscription/index.ts and gates everything on isSubscribed. To add IAP: a RevenueCat webhook endpoint upserts the same row with provider:'revenuecat' (or 'apple'/'google'). The provider-agnostic design (useSubscription.ts header comment: 'easy provider swap by only changing API endpoints') means the Vue side needs near-zero change.
- **StoreKit2 is now mandatory and RevenueCat abstracts SK1↔SK2 — but the IAP Key is a silent-failure trap** — Apple deprecated StoreKit1 APIs at WWDC 2024; new apps should ship StoreKit2 (RevenueCat SDK v5+ uses SK2 by default). RevenueCat handles SK1/SK2 transparently so existing subscribers transition seamlessly on the same bundle ID. THE GOTCHA: with Purchases v5.x+ (StoreKit2), 'transactions will fail to be recorded without [the In-App Purchase Key] being set, which can result in users not accessing the purchases they are entitled to.' ## Account Identity Spine (stable SSi ID + billing hard-link + verified support email + reconciliation)  —  _caveated_

The spine is feasible and the codebase is already 70% of the way there: learners.id (UUID) is a stable canonical account ID, verified_emails[] is a working multi-email merge mechanism, and the Paddle web checkout ALREADY hard-links payment to identity via customData.supabase_user_id echoed on every webhook. The genuinely-new work is (a) making the anonymous account server-persisted instead of localStorage-only — today a guest is a guest-<uuid> in localStorage that is DELIBERATELY excluded from every DB write, so a payer who never gave an email and reinstalls is unrecoverable, and (b) plumbing the IAP identity primitives (StoreKit2 appAccountToken, Google obfuscatedAccountId, RevenueCat appUserID) so a native IAP payer is resolvable by transaction. All four IAP primitives exist and are designed for exactly this; the hard parts are the anonymous-account migration, getting appAccountToken set at the RIGHT moment (StoreKit reads it at purchase init), and reconciling the existing messy base where guests left no server trace. The "support nightmare" is real and structural: Apple Hide My Email gives SSi a @privaterelay.appleid.com alias, and if the verified-email capture never fired there is no human-readable handle — the fix is to make the SSi-ID + transaction the primary lookup keys, with email as a third path.

**Key findings**
- **learners.id is already the canonical stable account ID; the work is persisting it earlier, not inventing it** — learners.id (UUID PK, 20251216193000_learner_tables.sql) is the FK target for enrollments/progress/subscriptions. learners.user_id (UUID, FK auth.users) is the auth identity. useAuth.ts computes learnerId from learner.value.id and is explicit that you must NEVER fall back to the auth UID. So a stable SSi-ID exists — but only AFTER sign-in. The spine's job is to mint it at first launch.
- **Today's anonymous identity is localStorage-only and NEVER server-persisted — this is the core gap** — getOrCreateGuestId() (useAuth.ts:65) writes guest-${crypto.randomUUID()} to localStorage. Every persistence composable (useLearningSession.ts:179 isGuestLearner, useBeltProgress.ts:170/179, useAdaptationEngine.ts:79, useListeningProgress.ts:73, usePodLapScheduler.ts:217) hard-EXCLUDES guest- IDs because the guest- prefix breaks the uuid column constraint (400 from Supabase). Consequence: a guest's progress lives nowhere server-side, and app-delete / new-device / clear-storage loses the identity entirely. A native IAP payer who paid as a guest is unrecoverable. This is the single highest-leverage fix.
- **Paddle web checkout ALREADY hard-links billing to identity — the pattern to replicate for IAP** — PremiumView.vue:203 opens Paddle.Checkout with customData:{ kind:'premium', supabase_user_id:userId }. paddle-webhook.ts:179 resolves learner via learners.user_id = customData.supabase_user_id and writes subscriptions.provider_customer_id (=Paddle customerId) + provider_subscription_id. So web payers are resolvable from a transaction TODAY. The IAP work is the exact analogue: appAccountToken/obfuscatedAccountId/appUserID = the SSi-ID, surfaced on the IAP webhook, resolved to a learner.
- **verified_emails[] is a working merge spine — reuse it, don't replace it** — learners.verified_emails TEXT[] (20260316_verified_emails.sql), GIN-indexed, column-REVOKEd from direct SELECT (20260401150001), read via get_my_verified_emails() RPC and find_learner_by_email() RPC. ensureLearnerExists (useAuth.ts:217-271) already does cross-email account linking: if a new auth email matches another learner's verified_emails, it re-points user_id and cascades to user_tags + govt_admins. api/email/verify.ts adds a second OTP-verified email and 409s if it belongs to another learner. This is exactly the 'reconcile by email' leg of the support-lookup story — already built.
- **All four IAP identity primitives exist, are UUID-shaped, and round-trip to the server** — StoreKit2 appAccountToken: UUID set at purchase init, returned in the JWS transaction + renewal info AND in App Store Server Notifications (so resolvable from any future transaction); a 2025 Set App Account Token endpoint lets you backfill it by transactionId. Google obfuscatedAccountId: <=64 chars, set via BillingFlowParams.setObfuscatedAccountId, retrieved via Purchase.getAccountIdentifiers() — MUST NOT be PII (use the SSi-ID UUID, not email). RevenueCat appUserID: pass the SSi-ID as a custom UUID at Purchases.configure(); logIn() merges an anon RC user into it; the custom ID flows through to the RC webhook. RevenueCat itself sets appAccountToken/obfuscatedAccountId for you when you set the appUserID, so RC is the simplest single integration that covers both stores.
- **No existing RevenueCat / StoreKit / Capacitor / anonymous-auth code — IAP identity is greenfield** — grep across packages + api for revenuecat/appUserID/appAccountToken/obfuscatedAccountId/StoreKit/Capacitor/signInAnonymously returned nothing. ProfileScreen.vue is entirely MOCK data (hardcoded learner@example.com). So the in-app account screen (point 4) and the whole IAP identity layer are net-new builds, not edits.
- **Supabase anonymous sign-in is the clean primitive for the server-persisted anonymous ID** — signInAnonymously() mints a real auth.users row + JWT at first launch; the learner row + all progress writes work immediately (no more guest- exclusion). Converting later via updateUser({email}) or linkIdentity() PRESERVES the same user id, so progress carries over with zero migration. This replaces the localStorage guest hack and makes the SSi-ID exist server-side from launch — directly enabling 'payer resolvable even with no email'. Caveat: it creates an auth.users row per fresh install (abandoned-install bloat) and needs RLS reviewed since anon users now hold real JWTs.
- **GDPR posture is improved, not threatened, by a single clean identity** — Hide My Email forwards from a per-app @privaterelay.appleid.com alias to the user's real inbox; SSi can still email them (configure the relay sending domain in Apple Developer console) but cannot see the real address. A single learners.id with verified_emails[] as the only PII store means access/export/delete requests resolve to ONE row + its FK cascades (ON DELETE CASCADE already on learners). The relay alias is just another entry in verified_emails.

## Cutover & rollout strategy (de-risking the swap)  —  _caveated_

The swap from a live Flutter app to a Capacitor-wrapped player-vue can be sequenced safely as an in-place binary update on the SAME bundle IDs, preserving reviews, ranking, and (critically) the running paid-install campaigns — the funnel attaches to the bundle ID/store listing, not the framework, so a framework change is invisible to the funnel as long as the bundle ID is held constant. Both stores support a native staged/phased rollout that maps cleanly onto a parity-gated soak, and Apple's phased release can be paused for up to 30 days. The genuine risks are NOT store mechanics — they are (1) the funnel can only be measured at full rollout because phased rollout splits ranking signal and conversion attribution thinly, (2) the payment-rail decision (keep IAP vs route to Paddle) is a hard gate that determines whether the existing IAP listing config survives the swap, and (3) the known-hard iOS lock-screen/background-audio battle (documented in CLAUDE.md, learnt twice) is the single most likely thing to regress against the Flutter baseline and must be a blocking parity gate. Keeping Flutter shippable as a fallback is cheap and essential during the soak window — but rollback on iOS is one-directional (phased release cannot revert; you ship a NEW build), so the real fallback is "halt + ship next build", not "roll back". The dev→staging→main weekly cadence maps onto store rollout with one added gate: a build only enters store phased rollout AFTER it has soaked on staging.saysomethingin.app as a PWA against real testers, because the store rollout clock is slow and one-directional and you do not want to burn a phased-release cycle discovering a regression the PWA soak would have caught.

**Key findings**
- **Same bundle ID = funnel survives the framework swap; this is the whole de-risking thesis** — The store listing, reviews, ranking, and ad campaigns (Apple Search Ads / Google UAC) all attach to the bundle identifier, not the app's framework. Shipping the Capacitor build as an UPDATE to the existing listing under the SAME bundle ID means the £1-2/install campaigns, the listing's review history, and search ranking carry over untouched — Apple/Play treat it as a continuous update of the same app. A NEW listing would reset reviews to zero, lose ranking, orphan the campaigns, and have no path to auto-migrate existing installed users. So: same bundle ID, update the existing listing. This is non-negotiable and is the lowest-risk path on every axis.
- **This is greenfield on the native-bridge side — zero existing Capacitor/StoreKit/Play-Billing code in the repo** — Verified: no ios/ or android/ dirs, no capacitor.config, no 'capacitor' references in player-vue or package.json, and zero RevenueCat/StoreKit/Play-Billing/cordova-purchase traces anywhere in packages/ or api/. All payment code today is Paddle (web): packages/player-vue/src/lib/paddle.ts + useSubscription.ts call /api/subscription/checkout which returns a checkoutUrl the app navigates to. Entitlement (useEntitlement.ts/useSubscription.ts) is entirely subscription-status-from-/api/subscription with NO native receipt validation path. Implication for cutover: the native payment rail is a from-scratch addition, so the cutover plan must NOT assume IAP 'just works' — the payment-rail decision (below) is on the critical path and is the hardest non-audio piece.
- **Payment-rail decision is the hard gate that determines whether the existing IAP listing config survives** — Tom's facts: they ALREADY take both IAP and web (Paddle) payments and the App-Store compliance is set up. Two cutover-relevant truths from research: (a) As of Dec 2025, the 9th Circuit modified the Epic injunction — US-storefront apps CAN include external purchase links/buttons without the External-Link entitlement, but Apple was granted the ability to charge a 'reasonable' commission on those external purchases (the 27% was struck, a successor fee is in play and litigated to the Supreme Court again). (b) This is US-storefront-specific; EU (DMA) is more permissive, rest-of-world generally still requires IAP for digital subscriptions consumed in-app. SSi is UK-based selling a £15/mo digital subscription — the safest assumption is that to KEEP the existing IAP setup and avoid re-review risk, the Capacitor build should continue offering IAP for the in-app purchase path (which means adding a native IAP plugin + receipt validation that does NOT exist yet), and may additionally surface an external Paddle link where permitted. Decision needed: does the swap keep IAP as primary (new native code, but funnel/compliance unchanged) or pivot to external Paddle (cheaper, but risks re-review and only safe per-storefront)? MUST CONFIRM what the live Flutter app actually does today (IAP SKUs, RevenueCat?) against the Flutter repo.
- **Both stores support native staged rollout that maps onto a parity-gated soak — but iOS rollback is one-directional** — Apple App Store phased release: automatic 7-day ramp at fixed 1/2/5/10/20/50/100%, can be PAUSED up to 30 days (unlimited pauses), but CANNOT be rolled back — to undo you make the version unavailable and submit a NEW build. Google Play staged rollout: you choose the user fraction, can HALT (stops new users getting it) and RESUME, halt+resume affects the same user set and % does not auto-advance. Practical consequence: 'rollback' on iOS is really 'pause + hotfix-forward', so the fallback strategy is keep-Flutter-shippable + halt-the-rollout + ship-the-fix, never 'revert the binary'. Play is more forgiving (true halt). Plan the iOS rollout assuming you get ONE shot per build and the pause button is your only live lever.
- **The repo already has a PWA-to-homescreen session hand-off bridge — reusable continuity signal, but a real account-continuity gap exists for existing Flutter users** — packages/player-vue/src/utils/authHandoff.ts (writeAuthHandoff/readAndConsumeAuthHandoff/isStandalone, wired in useAuth.ts) hands a Supabase session from Safari into a freshly-installed standalone PWA via CacheStorage. This proves the team has already solved 'carry a logged-in session across an install boundary' once. BUT: existing Flutter-app users who UPDATE to the Capacitor build will land in a fresh WebView with NO Safari session and NO Flutter session visible to it — they will be logged out and must re-authenticate (email OTP, useAuth.ts). For PAYING users mid-subscription this is a churn/support-ticket risk at the moment of cutover. This must be a designed migration step (in-app 'welcome to the new app, sign in with the email you used' + entitlement restored from /api/subscription once signed in), not an afterthought. MUST CONFIRM the Flutter app's auth identity (same Supabase email OTP? same learner identity?) against the Flutter repo — if it's the same Supabase auth, re-login restores everything; if not, there is a real identity-migration problem.
- **The iOS lock-screen/background-audio battle is the most likely Flutter-baseline regression and must be a blocking parity gate** — CLAUDE.md documents (lines 702-730) an explicitly 'learnt twice' iOS lock-screen/background-audio failure: keepalive hacks make the Control-Center widget flicker play/pause and audio dies after ~1 cycle. The ONLY working approach is useAudioSessionKeepalive (AudioContext silent oscillator). A pre-rendered-file Flutter app does NOT have this class of problem because it plays one long file — so the Capacitor build can REGRESS against the Flutter baseline specifically on locked/background playback even though it is better on sync-drift. A Capacitor WebView may also behave differently from Mobile Safari for AudioContext/MediaSession under lock. This is the #1 audio-failure-rate risk and must be an explicit go/no-go gate measured on real devices before any store rollout, plus a watched metric (audio-failure rate / 'stopped playing locked' support tickets) against the Flutter baseline during phased rollout.

## App-store policy + economics (CURRENT, cited)  —  _caveated_

A Capacitor wrap can keep SSi's working app-store funnel and is policy-compatible today, but the economics decision hinges on a landscape mid-flux. (1) Apple's Small Business Program is still the 15% rate while under $1M USD proceeds/yr (after Apple's cut) — SSi at ~£30k/mo consumer ≈ ~$340-360k/yr proceeds, comfortably under, so 15% is the baseline IAP tax, NOT 30%. Google Play matches at 15% for the first $1M/yr today. (2) In the US RIGHT NOW (verified Jan 2026), Apple may NOT charge any commission on external payment links — a 0% window after the Apr-2025 Epic injunction; the Dec-2025 Ninth Circuit upheld the ban but remanded to set a "reasonable" cost-based rate, so the 0% window is temporary and a fee is coming. (3) Apple guideline 3.1.3(b) multiplatform does NOT let SSi drop IAP — content acquired on web is accessible in-app, but IAP must still be offered; only true "reader" apps escape IAP, and a language course with active practice does not qualify cleanly. (4) EU sideloading/marketplaces are a distraction at SSi's scale. Bottom line: keep IAP for the funnel (the 3-5% conversion depends on frictionless tap-to-pay), add a US external-link button to harvest the 0% window while it lasts; the tax at 15% IAP on £30k/mo is ~£4.5k/mo — real but the conversion lift from in-app IAP almost certainly outweighs steering everyone to web.

**Key findings**
- **Apple SBP threshold is still $1M USD proceeds/yr; SSi is well under, so the IAP baseline is 15% not 30%** — App Store Small Business Program: 15% commission if you earned <$1M USD in PROCEEDS (i.e. after Apple's cut) in the prior calendar year, or are new. SSi consumer rev ~£30k/mo ≈ £360k/yr ≈ ~$455k gross → proceeds after 15% ≈ ~$390k — far under $1M. Threshold is across ALL associated developer accounts (can't split apps to dodge it). Exceed $1M mid-year → standard 30% applies to FUTURE sales that year; drop back below → re-qualify for 15% the FOLLOWING year. Government-contract revenue (~£30k/mo) does not flow through the App Store so does not count toward the threshold. Headroom: SSi could roughly double consumer revenue before the 30% cliff bites.
- **US external-link commission is 0% RIGHT NOW but this is a temporary, court-ordered window — a fee is coming** — Apr 30 2025 Epic v Apple ruling barred Apple from any commission on external-link purchases in the US and barred anti-steering (no restrictions on placement/format/content of in-app links/buttons, no full-page scare screens). Dec 11 2025 Ninth Circuit UPHELD the contempt finding but called the permanent zero-commission a district-court overreach and REMANDED to set a 'reasonable' cost-based rate plus IP compensation. Verified current state (Jan 2026): 0% remains in effect until the district court approves a specific rate; no rate set yet. So today a US app can show a 'Pay on the web' button at 0% Apple fee — but plan for a future fee (Apple's prior model was 27%; the new rate will be lower/cost-based but non-zero).
- **SSi cannot legally drop IAP via the multiplatform rule — it is not a clean 'reader' app** — Guideline 3.1.3(b) multiplatform lets users access content/subscriptions acquired on the web INSIDE the app (so a web-purchased SSi sub unlocks the wrapped app fine) — but only 'provided those items are also available as in-app purchases within the app.' IAP must still be offered. The IAP-free path is the Reader App rule (3.1.3(a)): magazines/books/audio/music/video as PRIMARY function. SSi's core is an interactive practice loop (prompt-pause-speak-feedback), not passive reading/listening of pre-purchased media, so it does not qualify cleanly for reader-app IAP exemption. Outside the US the External Link Account Entitlement is still needed even for genuine reader apps.
- **Google Play mirrors Apple's 15%/first-$1M today; a much cheaper US settlement regime is pending but not yet in force** — Current Google Play: 15% on first $1M developer revenue/yr, 30% after — same shape as Apple, SSi sits in the 15% band. The Epic v Google settlement proposes far lower US tiers (reported ~10% on auto-renewing subscriptions, ~20% on one-time IAP, plus a separate 5% billing fee for using Google Play Billing in US/UK/EEA; web link-outs taxed if purchase completes within 24h) with US/UK/EU rollout targeted ~30 Jun 2026 and a court approval hearing ~9 Apr 2026 — NOT final. Until then the existing Epic v Google injunction already allows alternative billing in the US. Android is structurally cheaper and more open than iOS for SSi.
- **EU is the cheap-payment frontier but the rules are a moving fee-stack; sideloading is a distraction at SSi scale** — EU external-link / alt-payment fees run ~10-20% (2% acquisition fee new-users-6mo + 5%/13% store services, SBP gets 10% on Tier 2 + 5% Core Technology Commission). Apple moves to a single Core Technology Commission model from 1 Jan 2026 (replacing the Core Technology Fee). Net: EU off-platform is cheaper than 15% IAP for established apps (~10%) but with admin overhead. EU alternative app marketplaces / sideloading are NOT worth pursuing at SSi's scale — they fragment the funnel for near-zero gain when paid-install ads point at the official stores.
- **The codebase already runs a web payment provider (Paddle) and a multiplatform-compatible web→app unlock — no IAP/StoreKit/RevenueCat code exists yet** — player-vue uses Paddle web checkout end-to-end: lib/paddle.ts (Paddle.js singleton), useSubscription.ts (checkout/portal/cancel via /api/subscription/*), useEntitlement.ts maps subscription→access (free through Yellow Belt then gated; community always free). PremiumView.vue opens Paddle.Checkout.open directly — pure web flow, no native store code. So the web payment rail and the entitlement-from-web-sub model (the 3.1.3(b)-compatible 'log in to access what you bought on web' pattern) already exist. To ship IAP in the Capacitor wrap, a NATIVE purchase layer (StoreKit2 / Play Billing, typically via RevenueCat) must be ADDED and reconciled with the same entitlement record — that is net-new work, flagged as the real cost, not policy risk.

**Risks**
- _(medium)_ US 0% external-link window closes mid-strategy: if the team designs the funnel to lean on the 0% web button and Apple's court-set fee lands (could be meaningful), the economics shift with little notice → Treat the 0% window as a bonus, not the plan. Keep IAP as the primary in-app path (15% is survivable) and add the external-link button as an additive US-only experiment. Architect the paywall so the link-out vs IAP choice is a server-side flag you can flip per region/rate without an app-store resubmit.
- _(medium)_ Apple rejects the wrap for steering if the external-link button or web-sub messaging breaks the still-binding rules outside the US (or US anti-steering nuance) → Region-gate the external-link button to the US storefront only (the RevenueCat guidance is to filter non-US traffic to IAP-only paywalls). Outside the US, offer IAP in-app and let web purchases unlock silently via 3.1.3(b) account login — never prompt iOS users toward web payment in-app outside the US.
- _(medium)_ Trying to claim reader-app status to escape IAP entirely gets the app rejected and burns review cycles (weekly-refresh cadence makes rejections costly) → Do NOT pursue the reader-app exemption — SSi's interactive practice loop won't qualify cleanly. Offer IAP; use 3.1.3(b) only to let web-purchased subs unlock the app. This is the low-risk, approvable posture.
- _(low)_ Crossing the $1M-proceeds SBP threshold (Apple) / $1M Google threshold quietly doubles the marginal tax to 30% on the consumer side → Monitor App-Store proceeds against $1M/yr. SSi has ~2x headroom on consumer revenue. The government-contract revenue does not route through stores so does not count. If consumer revenue approaches the cap, that is exactly when steering high-value renewals to web (0% or low external-link fee) pays off most.
- _(medium)_ Adding a native IAP layer (StoreKit2/Play Billing/RevenueCat) introduces a second source of truth for entitlement that can diverge from the existing Paddle/Supabase record → Funnel both rails into one entitlement row in Supabase (the useEntitlement/useUserEntitlements model already centralizes this). RevenueCat can normalize StoreKit2 + Play Billing webhooks into the same backend the Paddle webhook already writes; reconcile on a single user→entitlement key.

**Recommendations**
- KEEP in-app IAP as the primary paywall in the Capacitor wrap. At SSi's scale the rate is 15% (SBP/Google first-$1M), not 30%, and the frictionless tap-to-pay is what produces the 3-5% month-1 conversion the funnel is built on. The ~£4.5k/mo tax at 15% on £30k/mo consumer revenue is the price of that conversion lift — losing even a fraction of 3-5% by steering everyone to web would cost more.
- ADD a US-only 'Pay on the web' external-link button as an additive experiment to harvest the current 0% commission window, region-gated to the US storefront. Run it as an A/B against IAP-only; measure whether the web conversion holds up enough to beat 15% IAP. Build it behind a server-side flag so you can disable or re-price it the moment Apple's court-set fee lands.
- REUSE the existing Paddle web rail for the 3.1.3(b) 'log in to access' path so web-purchased subscriptions unlock the wrapped app cleanly (already supported by useEntitlement/useSubscription). This is the compliant way to let people who DO convert on web use the app — no policy risk.
- Do NOT pursue reader-app IAP exemption or EU alternative marketplaces / sideloading — neither is approvable/worth it at SSi's scale and both fragment the working paid-install funnel.
- Plan native IAP integration via RevenueCat (or direct StoreKit2 + Play Billing) reconciled into the SINGLE existing Supabase entitlement record — this is the genuine net-new engineering, sized as such, and the only hard part of the payment side of the wrap (policy is not the blocker; the dual-rail entitlement plumbing is).
