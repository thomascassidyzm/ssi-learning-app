# Android bottom-controls clearance — landed, and what is still unproven

**2026-09-05.** Closes the collision Deborah reported. Companion to
`bottom-clearance-2026-09-05.md`, which is the design record for the fix itself.

## The landing state that mattered

The fix was written the same morning as job #582 and **was never merged**.
`git cherry origin/dev origin/cs/582-android-bottom-controls-must-cle` returned
two `+` lines, and `origin/dev` still carried the pre-fix rule in both places:

```
components/BottomNav.vue:304        bottom: max(calc(env(safe-area-inset-bottom, 0px) / 2), 12px);
components/LearningPlayer.vue:18974 bottom: max(calc(env(safe-area-inset-bottom, 0px) / 2 + 82px), 94px);
```

So the answer to "did that land" was no, and that is very likely the whole of
what Deborah is looking at. The work here was to land it, not to write it again.

## The reproduction, before anything was changed

`e2e/_android-clearance-harness/probe.mjs` with `?legacy=1`, which restores
dev's rule verbatim, at the three postures. Pixel-7 viewport, real BottomNav,
real tokens:

| reported inset | dev's rule | gap above the bar | verdict |
|---|---|---|---|
| 0px | 12px | +12px | under the 16px touch margin |
| 24px (gesture) | 12px | **−12px** | 12px inside the strip |
| 48px (three-button) | 24px | **−24px** | 24px inside the bar |

After the fix, at the same three: +24 / +16 / +16, and `elementFromPoint` at
every control's own centre returns that control.

**The zero-inset row is Kai's screenshot** — a real but thin gap, which is why
his OnePlus does not reproduce the collision. The other two rows are Deborah's
complaint. One rule, three outcomes.

## Is the cause navigation mode?

**Partly, and the honest answer is that we do not know which posture Deborah is
in.** Navigation mode changes the reported inset (roughly 24px gesture vs 48px
three-button), and the old rule fails at both — worse at three-button. But the
zero-inset posture, where Capacitor has padded the WebView out of the bars, also
fails the touch margin at 12px. All three are the same defect. Which one Deborah
sees is a fact about her handset that this box cannot obtain; the questions to
her, and the `insets t/r/b/l · source` read-out on the Settings build card that
answers it in one glance, are in the published doc.

## What keeps it fixed

`src/platform/scanBottomChrome.ts` + `bottomChromeOffsets.test.ts`, in the shape
of the existing `scanPlatformDoors`. Run over `origin/dev`'s own source tree it
returns **nine hits across six files**, including both lines above. It runs in
`pnpm --filter player-vue test`. It governs the bottom *offset*; it deliberately
leaves `padding-bottom` on scroll containers alone — that is content clearance,
already uses the full inset, and cannot put a control inside the bar.

To re-run the geometry proof: `node e2e/_android-clearance-harness/probe.mjs`
from `packages/player-vue` (needs the workspace installed).

## The gap, named

**No real-device evidence was produced here.** `/dev/kvm` does not exist on
watson-1: no hardware virtualisation, no AVD, no system image. A Chromium
hit-test at a simulated inset is not a phone, and a browser viewport has no
system navigation bar at all — which is exactly how job #632 verified a
bottom-controls fix at 420x860 and could not have seen this defect.

A debug APK of the merged code was built —
`~/apk-serve/ssi-devwrap-7ccf1288-debug.apk`, 23,347,632 bytes, sha256
`25288a3e2d550e79539b07fdefc76ab117525dcdb83ebc1db081a7a30364f53c`. **It is not
downloadable from anywhere yet**: `popty.app/builds` returns the dashboard SPA
shell for every path, including the previous build's own filename, so the route
#582 recorded does not serve APKs. Somebody with the distribution path needs to
put it where Kai can reach it.

And the thing to say to Deborah plainly: the web assets are baked into the
installed APK, so **no merge, no reload and no "tap to update" carries this fix
to her handset.** Only installing a new build does.
