# iOS: what it costs, what it changes, and the sequence only you can run

**2026-09-05, job #558. The floor, first: an `.ipa` can only be produced on macOS with
Xcode; the box this ran on is Linux, so nothing here built, signed, uploaded or shipped
one.** What this job did do: determined the Apple membership question from public data,
generated the iOS Xcode project (unverified, by definition), audited every place iOS
diverges from the Android wrapper with each claim labelled *verified* or *asserted*,
ruled the staleness-line design question and implemented the ruling, and wrote the
ordered sequence below for your Mac. Everything sits on the unmerged branch
`cs/558-ios-cost-divergence-and-the-mac-`.

**What that proves and what it doesn't.** Apple removes apps from sale when a

## 2. What already exists, and what this job added

**The Capacitor wrapper rides to iOS almost unchanged — verified in code, not assumed:**

- **The platform seam is one door** (`src/platform/capabilities.ts`), stamped into the
  built `index.html` post-build. iOS uses the identical mechanism; there is no second
  build and no iOS-specific fork in `src/`.
- **CORS is already iOS-ready.** `api/_utils/cors.ts` line 59 allowlists
  `capacitor://localhost` alongside Android's `https://localhost` — someone wired the
  iOS convention in advance. The two audio routes (`/api/audio/:id`, batch-urls) emit
  `Access-Control-Allow-Origin: *` and accept anything. And the shipped Capacitor 8
  CLI's own type declarations state `iosScheme` **cannot be set to http or https**
  (WKWebView reserves them), so `capacitor://localhost` is not a choice, it's the
  floor — and the API already accepts it. Auth is bearer-token with
  `credentials: 'omit'`, so no cookie `Secure`/`SameSite` trouble exists to have.
  One rider: `api/_utils/cors.ts` exists **only on `dev`** — staging/main cannot answer
  any wrapper until it rides the promotion train.
- **The plugin audit came back empty, honestly.** The app uses zero community
  Capacitor plugins — only core + the Android platform. So "audit every plugin for iOS
  support" has a one-line answer, and the real question underneath is *what does the
  app get from the browser that WKWebView won't give it* — that's §4.
- **Payments are already abstracted.** `paymentRoute.ts`: `webview → 'store'`,
  `STORE_BILLING_WIRED = false`, every affordance gates on `canTakePayment()`, seat
  purchase excluded at build time. iOS needs no new abstraction, only the StoreKit
  wiring behind the existing one (§4).

**Added by this job, on the branch, all UNVERIFIED on any Apple hardware:**

- `packages/player-vue/ios/` — the real Xcode project, generated by `npx cap add ios`
  on this box. Capacitor 8's template is **Swift-Package-Manager based: there is no
  CocoaPods step at all**, which removes a classic Mac-side failure mode. Deployment
  target iOS 15.0 (matching the live listing's minimum, coincidentally). It inherited
  the deliberately-throwaway bundle id `com.saysomethingin.devwrap` — presuming
  nothing. Nothing about this tree has been compiled; Xcode may still want signing
  changes, asset fixes, or a Capacitor sync once `dist/` exists.
- Two hand edits to its `Info.plist`, each flagged unverified in its own comment:
  `UIBackgroundModes: audio` (necessary for locked-screen audio, not sufficient — §4)
  and `NSMicrophoneUsageDescription` (PronunciationOverlay calls getUserMedia;
  on iOS that's a **process kill**, not a denied prompt, without the string).
- The staleness-line ruling, implemented (§3).

## 3. The design ruling: TestFlight breaks the Android update model — here is the answer

**The provenance row stays identical on iOS. Ruled, no code needed.** The commit sha
and API origin are facts about the artefact, not the channel; Kai naming the sha in
his first Android report is the row earning its keep. TestFlight shows its own
build/version number and the two *can* legitimately disagree — the row names the web
code inside, TestFlight numbers the native archive around it; the same web sha
re-archived is a new TestFlight build and the same row. Adding TestFlight's number to
the row would need a native bridge with no consumer — fails Simpler and Cheaper, not done.

**The staleness line goes SILENT on iOS. Ruled AND implemented** (commit on this
branch; `shouldDescribeStaleness()` now answers no when the shell's OS is iOS,
`injectPlatform.mjs` grew an optional `android|ios` third argument, an unstamped shell
stays loud so every existing Android stamp keeps the cure). Why silence and not
rewording — this is a position, not the fallback, though it agrees with the
conservative default:

1. The governing ruling is *a waiting state must promise the resolution that actually
   exists*. On Android the promise holds structurally: popty.app/builds serves the
   newest APK **on demand** — if the comparison fires, the remedy exists. On iOS the
   comparison ("the web deployment is newer than my bundled assets") does **not**
   imply any newer TestFlight build exists to install — uploads are manual, reviewed
   and slower. "Update it in TestFlight" would regularly point at nothing. That's the
   same lie as `popty.app/builds`, in different clothes.
2. When a newer build HAS been uploaded, TestFlight notifies the tester itself and
   offers the update button. Our line would duplicate a platform affordance, with less
   authority and no button.
3. `buildStaleness.ts` rule 2 is *silent when unsure*. On iOS we are structurally
   unsure. So: silent — no new i18n key, no fork of `appBehindLive`, and the test that
   pins the Android wording is untouched and still green.

One cost this dodges, now stated as fact rather than guess: `appBehindLive` exists in
**1 of 25 locale files** (verified). A reworded iOS variant would have forked that
localisation debt per-platform. Silence costs zero words in zero languages.

**The 90-day expiry — the staleness class Android never had: the app says NOTHING,
also ruled.** An expired TestFlight build refuses to *launch*; Apple's own screen
appears and our code never runs, so a post-hoc message is impossible, and a
pre-emptive countdown ("this build expires in N days") would need the upload date the
web assets can't know, duplicate TestFlight's own expiry notices, and put an
unactionable warning in a learner's face. The expiry is an **operational cadence for
you** — upload a fresh build comfortably inside every 90 days while TestFlight is the
channel — and it's step 10 below, not copy.

**The mechanism confirmation the brief asked for:** yes — the comparison plumbing
works unchanged on iOS (bundled `/version.json` still frozen, API origin still
reachable) and this is purely a copy-and-policy fork. It lives in `capabilities.ts`,
the one door, not in `buildStaleness.ts`, which stays platform-blind.

## 4. What else diverges — verified vs asserted, item by item

**Audio and background playback — the go/no-go only a real iPhone can answer.**
*Verified:* the oscillator keepalive (`useAudioSessionKeepalive.ts`) exists and is the
thing that works on the PWA; WKWebView is the same WebKit engine, so the wrapper is no
worse than the PWA. *Asserted from the prior art and Apple's model:* iOS adds three
levers a PWA never had — `UIBackgroundModes: audio` (now in the scaffold's
Info.plist), an `AVAudioSession(.playback)` category held by ~5 lines of Swift in
`AppDelegate`, and real lock-screen/now-playing controls. **Whether the keepalive hack
is still needed under a held AVAudioSession is binary and undeterminable from here.**
The first hour with a device is: build, play, lock the screen, wait 30 minutes. Not a
probability — a coin whose face only a device shows.

**Offline storage.** *Verified in CLAUDE.md's measured figure:* a full `spa_for_eng`
offline download is ≈1.86 GB, ~1.9× over Safari's ~1 GB PWA cap. *Asserted, needs
device confirmation:* inside a native app's WKWebView the WebKit quota is tied to the
app, not the ~1 GB web-origin cap, and is substantially larger in practice — but
IndexedDB inside WKWebView remains WebKit-managed and evictable under storage
pressure; the known escape (prior art, still right) is moving downloaded audio to the
app container via the Filesystem plugin — a fast-follow, not day one. *Verified by
construction:* the bundled `dist/` assets are app payload — never subject to WebKit
quota, but they count toward the App Store download size (the Android APK is 22 MB;
the live Flutter iOS app is 110 MB — headroom is not the worry).

**IAP — one paragraph, as ordered.** The India design (/d/d3f122a8) is one product id,
price never in the id, the country carrying the number via the store's per-country
price table — and Apple has exactly the same per-country subscription price mechanism,
so the design ports without a line changing; `paymentRoute.ts` already routes
`webview → store`. What StoreKit adds over the Play route: App Store Connect product
setup under the chosen bundle id, the **StoreKit2 In-App Purchase Key uploaded to
RevenueCat** (its absence silently fails to record transactions — the #1
payer-orphaning cause, from the prior analysis, unverifiable from here), and Apple's
cut — 30%, or **15% under the Small Business Program** (<$1M/yr, needs enrolment,
check in the ten-second visit). None of it is day-one: `STORE_BILLING_WIRED = false`
keeps every payment affordance honestly dark on iOS exactly as on Android, and a
TestFlight build with payments dark is fine for testers.

**Push.** Nothing changed — no push code, no plugin, CLAUDE.md's "not needed for
learning" stands. One line, moving on.

**The install prompt.** *Verified:* the seam already answers it —
`shouldOfferAppInstall()` returns false in any webview, and `InstallBanner.vue`
consults the seam. If the banner still shows in the Android build, that's the banner
not asking (same fix both platforms); iOS has no `beforeinstallprompt` at all, so if
anything the failure is quieter there. Same fix, once, at the seam consumer.

**Service worker / secure context.** *Verified:* `shouldRunServiceWorker()` already
gates the SW off in any webview, so WKWebView's patchy SW support costs nothing.
*Asserted:* Capacitor treats `capacitor://localhost` as a secure context, so
`crypto.subtle` and `getUserMedia` work — the mic needs the Info.plist string (added)
and a first-use permission prompt.

## 5. The ordered Mac-side sequence — only you can run this

Steps marked **HIS** are irreversible or gated on accounts only you hold; everything
else a worker can prepare or script later. Times are honest estimates.

1. **HIS — Membership (10 sec–2 days).** developer.apple.com/account → Membership.
   Current? Note the team name and whether SBP shows enrolled. Expired → renew ($99,
   minutes). Can't sign in → find the Account Holder before anything else; if a fresh
   enrolment were ever needed it's 1–2 days of Apple verification, but §1's evidence
   says that's unlikely.
2. **HIS — The bundle id decision (one sentence, forever).** The sharpest irreversible
   on this page: **an id, once any build is uploaded to App Store Connect under it,
   can never be renamed and never be reused**, even after deletion. Three doors:
   **(a)** `com.saysomethingin.apple` — the live listing: TestFlight builds sit under
   the existing app, and eventual release **updates the app under every existing user
   of it**, inheriting reviews, ranking and the funnel; **(b)** a fresh id — a clean
   parallel listing, existing users untouched, install base starts at zero;
   **(c)** for pure TestFlight testing you may create a *separate throwaway* id (e.g.
   a dev-wrap id) and decide (a)-vs-(b) later — TestFlight-only uploads under a
   throwaway never touch the public listing, but the throwaway id itself is still
   burned forever. Getting (a) wrong ships a WebView over live payers' heads;
   getting (b) wrong abandons the funnel. Yours alone. Nothing on the branch presumes
   any of them — the scaffold carries the local dev id, which is not usable for upload.
3. **HIS — App Store Connect API key (5 min, do it while you're in there).** Users
   and Access → Integrations → App Store Connect API → Team key, role App Manager.
   Download the `.p8` **once** (it cannot be re-downloaded; note the Key ID + Issuer
   ID). This is the thing that makes every later step scriptable (Fastlane/CI) without
   your password — the single highest-leverage five minutes on this list.
4. **HIS — Identifier + capability (5 min).** Certificates, Identifiers & Profiles →
   register the chosen bundle id, tick **Background Modes** (the Info.plist side is
   already in the scaffold). No other capability is needed day one.
5. **HIS — App Store Connect app record (5 min).** "New App" against the bundle id
   (skip if door (a) — the record exists). Name, primary language, SKU.
6. **Mac — clone + build the web artefact (15 min).** Branch
   `cs/558-ios-cost-divergence-and-the-mac-`; `pnpm install`; `pnpm --filter @ssi/core
   build && pnpm --filter player-vue build`; stamp it —
   `node scripts/injectPlatform.mjs dist/index.html https://ssi-learning-app-git-dev-zenjin.vercel.app ios`
   (the `ios` argument is what makes the staleness line correctly silent); then
   `npx cap sync ios`. Point at **dev** — it's the only deployment whose API answers a
   wrapper today.
7. **Mac — Xcode: open, sign, run (30 min first time).** `npx cap open ios`; Signing &
   Capabilities → your team, automatic signing (Xcode mints the development cert and
   profile itself — don't hand-create certificates; hand-managed signing is the classic
   place hours die). Set the bundle id from step 2. Run on a **real iPhone** first —
   and do the audio go/no-go from §4 before anything else: play, lock, 30 minutes.
   That result reshapes everything downstream.
8. **Mac — archive + upload (20 min).** Product → Archive → Distribute → App Store
   Connect → Upload. Automatic signing makes the distribution cert too. Processing
   takes ~15–30 min server-side, then the build appears in TestFlight. First upload
   under a new id may ask for export-compliance answers (standard HTTPS = exempt).
9. **HIS — TestFlight groups (10 min) — this distinction sets the tempo.**
   **Internal testers** (up to 100, must be App Store Connect team users): builds
   reach them with **no Beta App Review — within the hour of processing**. **External
   testers** (up to 10,000, email or public link): the first build of each version
   needs **Beta App Review**, typically ~a day. So: add Kai (and yourself) as team
   users → internal group → testing today; Deborah and anyone outside the team ride
   the external lane a day later. TestFlight's own app handles their installs and
   update notifications from here — which is exactly why §3 keeps our copy silent.
10. **Operational clock — builds expire 90 days after upload** and then refuse to
    launch. While TestFlight is the channel, a fresh upload comfortably inside every
    90 days is part of the cadence. (Steps 6–8 are one Fastlane lane once step 3's key
    exists — a worker job, later, unverifiable from Linux today so deliberately not
    written now.)

**Review-risk note for the eventual public release (not TestFlight):** Guideline 4.2
minimum-functionality is the known rejection class for WebView apps. This app's
answer is real — offline learning, a genuine audio engine, background audio — but it
must be *wired and demonstrable*, and payments must be IAP, never Paddle, in the
store build (`paymentRoute.ts` already enforces that). Beta App Review is lighter
than full review; first-version full review is the clock you don't control.

## 6. Explicit gaps — what this box could not determine

- Membership currency, Account Holder identity, SBP enrolment, existing IAP products,
  existing certs/keys under the team (§1's ten-second visit answers all five).
- Whether the scaffolded Xcode project compiles. Generated, never built. Treat every
  file under `ios/` as plausible until Xcode says otherwise.
- The locked-screen audio go/no-go. Binary, device-only (§4).
- The real WKWebView storage quota behaviour for a 1.86 GB course under a native app.
- Whether the keepalive oscillator harms or helps once a native AVAudioSession holds
  the session (device-only).
- What the live `com.saysomethingin.apple` app's IAP products/subscribers look like —
  door (a) in step 2 inherits real payers, and nothing here could see them.
