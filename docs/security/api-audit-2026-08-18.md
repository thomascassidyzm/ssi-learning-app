# API security audit — 2026-08-18

**Scope.** The serverless API surface in `api/` (≈180 endpoints + 60 shared utils), read for
auth boundaries, input handling, and the shape of the request→service-role path. Static review
plus executable tests. **Nothing was fired at production, nothing was patched, no live behaviour
changed.** Findings only.

**Method.** Every endpoint that instantiates a service-role Supabase client (107 of them) was
checked for an authorisation reference; the twelve with none were read in full. On top of that:
injection primitives (PostgREST filter strings, `ilike`/`like` patterns), mass-assignment spreads
into writes, webhook signature verification, secret generation, rate limiting, CORS, redirects,
and the impersonation path.

**How to read the findings.** They are executable. Each one is a spec that is red today:

```bash
pnpm run test:security-audit     # 5 failing assertions = 3 findings (was 8 = 5)
```

The specs live on a `*.security-audit.ts` suffix under `vitest.security-audit.config.ts`, kept
out of the CI-gated `pnpm run test:api` glob on purpose — a merge gate that is permanently red
stops being a gate. Nothing is skipped or marked expected-to-fail; the failures are real. A
finding is fixed when its spec goes green, at which point it should be renamed to `*.test.ts` so
CI holds the line from then on.

Finding 6 is the exception: it is a *characterisation* test, it passes, and it pins down the
limit of a control rather than a defect in it. It rides in the gated suite.

## Finding 1 — govt_admin invite codes are minted from `Math.random()` · High

`api/admin/create-govt-admin.ts` carries its own private code generator:

```ts
function generateInviteCode(): string {
  const part = () => Math.random().toString(36).slice(2, 5).toUpperCase()
  return `${part()}-${part()}`
}
```

The repo already has the ruling on this class of secret, written into `api/_utils/codeGen.ts` in
its own words: these codes "gate elevated `educational_role` grants
(teacher/school_admin/govt_admin) into a school/group on redemption, so their minting must not be
predictable from observed samples" — which is why `generateCode()` uses `crypto.randomInt`.
This endpoint does not use it, and the code it mints is the **highest-privilege invite in the
system**: `api/code/redeem.ts`'s `codeType === 'govt_admin'` branch writes `educational_role`,
creates the `groups` node if absent, and inserts a `govt_admins` row — leadership over a whole
region subtree.

`Math.random()` in V8 is xorshift128+. It is not a CSPRNG and does not claim to be: its internal
state is recoverable from a modest run of observed outputs, after which every subsequent value —
and, running the generator backwards, every prior one — is derivable. Codes are minted one per
request from a warm serverless instance, so outputs from one instance are correlated.

Nominal keyspace is also thin at ~2.2 × 10⁹ (two 3-char base36 parts), which only matters
because of Finding 2 — but predictability is the primary defect, and it does not need the
keyspace argument.

**Failure scenario.** An attacker who can observe a handful of values derived from the same
instance's `Math.random()` recovers the PRNG state and computes the next govt_admin code without
guessing. The spec demonstrates the weaker, unarguable half of this: with `Math.random()` driving
generation, two mints from the same PRNG state produce an identical secret.

**Fix.** Delete `generateInviteCode()` and call the shared `generateCode()` (or
`generateShareCode()` for a wider keyspace) from `api/_utils/codeGen.ts`. One import; format
unchanged if `generateCode()` is used.

**FIXED 2026-08-18.** `generateInviteCode()` is deleted; the endpoint mints through the shared
`generateCode()` behind the same unique-code retry loop `api/invite/create.ts` uses. The spec
graduated to `create-govt-admin.codeEntropy.test.ts` in the gated `pnpm run test:api` suite, with
a third assertion pinning the shared generator's alphabet and shape so a future private generator
cannot creep back in.

## Finding 2 — `/api/code/redeem` is an unthrottled enumeration oracle · High

Two sibling endpoints name this exact threat and defend it. `api/code/validate.ts`, in its own
comment:

> "this endpoint is unauthenticated and returns a discriminated `{valid, codeKind, ...}` for any
> submitted string, so without a throttle it is a code-enumeration oracle: the ~13.8M ABC-123
> keyspace is sweepable, and a hit yields an elevated-role invite
> (teacher/school_admin/govt_admin) that the sibling possession-redeem path turns into a session
> — i.e. school infiltration."

`api/auth/possession-redeem.ts` carries per-code **and** per-IP limits for the same reason.
`api/code/redeem.ts` has neither.

It requires a bearer token, and that is doing less work than it looks like: sign-up is open
self-service email OTP, so "authenticated" costs an attacker one throwaway mailbox. And unlike
`validate.ts`, a hit here does not merely *report* the code — it **redeems** it. The branches
write `platform_role = 'ssi_admin'`, `platform_role = 'tester'`,
`educational_role = 'school_admin' | 'teacher'`, and create the `govt_admins` row.

Every miss returns a uniform, free `200 {success:false, error:'Invalid code'}`. No attempt row,
no counter, no cost.

**Failure scenario.** One throwaway account sweeps the ABC-123 keyspace against
`POST /api/code/redeem` with `{codeKind:'invite'}`. The spec drives 200 consecutive wrong guesses
from a single account and a single IP; all 200 reach the code table and all 200 return 200.

**Fix.** Give redeem the throttle its siblings already have — the `possession_mint_attempts`
table and window logic are already written and already shared by three endpoints. Key it on
account **and** IP (see Finding 5 for the IP half). Cheap, and it reuses existing machinery
rather than adding any.

**FIXED 2026-08-18.** The counting logic is now a shared module,
`api/_utils/codeAttemptThrottle.ts` — same table, same 15-minute window, same per-IP limit of 10,
same uncounted-outcome rule as both siblings — and `redeem.ts` runs it before any code lookup,
logging every attempt and 429ing over the limit. Per-**IP** only, matching the siblings exactly:
the account half is not added here because the IP bucket is the one the siblings share, and
adding an unindexed `auth_user_id` count would need a migration for a second control against the
same sweep. `auth_user_id` *is* written on every attempt row, so the account-keyed limit is a
query away when wanted. The two siblings keep their pre-existing inline copies of the helpers;
migrating them onto the shared module is the natural moment to fix Finding 5, which touches
`getClientIp` in all three at once. The spec graduated to `redeem.throttle.test.ts` in the gated
suite.

## Finding 3 — mass assignment into `lego_progress` · Medium

`api/school/class-progress.ts` is a careful endpoint, and its docstring is right about the
boundary it was designed to hold: "args EXCLUDE `learnerId` and `courseId`; both are resolved
server-side from the class row … so a caller can never target an arbitrary learner or course."
That property holds for the **signature**.

It does not hold for the **payload**:

```ts
async function updateLegoProgress(svc, learnerId, id, updates: Record<string, any>) {
  // …ownership pre-check: this row belongs to `learnerId`…
  await svc.from('lego_progress').update({ ...updates, updated_at: … }).eq('id', id)
}
```

`updates` is `args[1]`, straight from the request body — the handler says so itself: "Client-
supplied and untyped by design … (Input validation of these is a separate concern, not this
pass.)". The ownership check proves the row belongs to the class learner *before* the write, and
the write is then free to change which learner it belongs to. `learner_id`, `course_id`, and
every other column of `lego_progress` are caller-writable.

This is **the only `...spread` into a Supabase write anywhere in `api/`** — every other endpoint
enumerates its columns. It is an outlier, not a pattern.

**Reachability.** Any teacher or school_admin with the class in their visible scope — the
endpoint's intended callers, not outsiders. Blast radius is "a teacher can corrupt progress rows
outside their class", not remote takeover. It is a real boundary all the same: the whole reason
this endpoint exists is that the browser is not trusted to write these rows directly, and the
untyped passthrough hands part of that trust back.

**Failure scenario.** `POST /api/school/class-progress` with
`{method:'updateLegoProgress', args:['<row-id>', {learner_id:'<victim>', reps_completed:1}]}`
moves a progress row onto another learner.

**Fix.** Enumerate the writable columns, exactly as `saveLegoProgress` two functions above
already does.

## Finding 4 — PostgREST `.or()` filter injection · Medium

Same root cause, different consequence. Two methods build filter expressions by string
interpolation of caller-supplied values:

```ts
.or(`last_completed_round_index.is.null,last_completed_round_index.lte.${roundIndex}`)   // setLivePosition
.or(`last_completed_lego_id.is.null,last_completed_lego_id.lt.${ratchetHighestTo.legoId}`) // setMode
```

`.or()` takes a **raw PostgREST filter expression**, not a bound parameter. A comma in the value
adds a disjunct, and `or` is satisfied by any disjunct.

What those clauses exist to enforce is the **forward-only ratchet** — never move a learner's
recorded position backwards. A caller who injects `,last_completed_round_index.gte.0` dissolves
that guard entirely; the update becomes unconditional.

**Failure scenario.**
`{method:'setLivePosition', args:['S0001L01', '0,last_completed_round_index.gte.0', 0]}` — the
spec asserts the built filter has exactly the two disjuncts the code intends and gets three.

**Fix.** Coerce before interpolating (`Number(roundIndex)`, reject `NaN`; validate `legoId`
against `/^S\d{4}L\d{2}$/`), or express the ratchet as a read-then-conditional-write. Coercion is
the smaller change and closes both call sites.

> Findings 3 and 4 share one cause — `const a: any[] = Array.isArray(args) ? args : []` forwarded
> positionally into fifteen methods. Validating at that seam once is a smaller fix than fifteen.

## Finding 5 — the throttle bucket is keyed on a header the caller sets · Medium

Three endpoints share one limiter (the `possession_mint_attempts` table) and one identical helper
— `api/code/validate.ts`, `api/auth/possession-redeem.ts`, `api/try-link/validate.ts`:

```ts
function getClientIp(req) {
  return (req.headers['x-forwarded-for'])?.split(',')[0]?.trim()
      || (req.headers['x-real-ip'])
      || 'unknown'
}
```

`X-Forwarded-For` is a hop list and the **leftmost entry is the one the original client wrote**.
Reading position 0 is reading attacker input; so is `x-real-ip`, which any client can send.

**Honest limit on this one.** Whether a forged value actually *reaches* the function depends on
whether the edge in front of it strips or overwrites the header. That is a property of the
deployment as much as the code, and it has **not** been verified against the live Vercel edge —
this pass fired nothing at production. So: PLAUSIBLE, not CONFIRMED, on exploitability.

What the code can be held to regardless is the defensive shape: the throttle bucket should not be
derivable from client-controlled headers when a platform-attested source exists (Vercel exposes
`x-vercel-forwarded-for`; `req.socket.remoteAddress` is the transport truth).

Why it matters more than a routine limiter bypass: `validate.ts`'s own comment says this limiter
is the only thing between an anonymous caller and a sweep of the 13.8M keyspace. A per-IP window
of 10 that resets when you increment a header is a formality, not a limit.

**Failure scenario.** A sweep that rotates its declared `X-Forwarded-For` every request never
accumulates a window. The spec drives 25 attempts from one socket with 25 declared IPs and
asserts they land in one bucket; they land in 25.

**Fix.** Prefer `x-vercel-forwarded-for` (platform-set), then `req.socket.remoteAddress`; treat
`x-forwarded-for`/`x-real-ip` as untrusted. One helper, three call sites — it is already
duplicated identically in all three, so extracting it is a net simplification.

## Finding 6 — "read-only while viewing as" is advisory · Low

`rejectIfViewAs()` decides whether a request is a read-only view-as request by reading
`X-Ssi-View-As: 1` — a header the client chooses to send. The guard is straight about this in its
own docstring, and for its stated purpose the choice is sound: it exists to stop an admin's
`ssi_admin` support bypass firing **by accident** while they browse as a persona, and an honest
client always sends it.

What it cannot do is bind an admin who does not want to be bound. Omit the header and the support
bypasses in `class-teachers.ts` / `create-class-join-code.ts` / `create-class-learner.ts` fire
normally.

That matters only because of what `api/admin/view-as.ts` claims for its audit rows: "This IS the
GDPR legitimate-interest compliance record". The record says read-only; the server cannot prove
read-only.

**Fix, if the compliance claim is to be load-bearing.** Server-side session state — a view-as
session opened by `view-as.ts` `'start'` and closed by `'end'`, consulted by the bypass endpoints
— so the audit row and the enforcement read from the same fact. Written down rather than
prescribed: this is a judgement call about how much weight the compliance record is meant to
carry, and that is not the auditor's call to make.

## Assessed and *not* findings

Worth recording, so the next pass does not re-litigate them:

- **`Access-Control-Allow-Origin: *` on seven endpoints** (`player-events`, `entitlement/offline-lease`,
  `school/subscription`, `subscription/index`, `org/subscription`, `audio/batch-urls`,
  `audio/[audioId]`). No `Access-Control-Allow-Credentials`, and these authenticate by `Bearer`
  header rather than cookie — so a browser never attaches credentials cross-origin, and a
  malicious page gains nothing it did not already have. Not exploitable. Noted only because the
  pairing of `*` with `Authorization` in `Allow-Headers` reads alarming and will keep being
  re-flagged.
- **Paddle and Wise webhooks.** Both verify properly — Paddle via `paddle.webhooks.unmarshal`
  against the raw body with `bodyParser: false`, Wise via RSA `createVerify` against the
  published public key. The A-123 work (`cfff6afc`, `1ccdd638`) closed the payer-binding hole and
  its regression tests are in the gated suite.
- **`api/family/signin-link.ts`.** The obvious attack — mint a magic link for an arbitrary
  account — is closed: ownership is checked against `family_members.owner_learner_id`, and
  `is_child_account` is required. `create-child.ts` only ever mints synthetic
  `fam-<uuid>@members.saysomethingin.app` addresses, so a parent cannot create a "child" over
  someone's real email and then re-mint into it.
- **`api/access/claim.ts`.** Email comes from the verified session (`auth.getUser(token).email`),
  never the body. Correct.
- **`api/auth/cascade-user-id.ts`.** Carries a real risk and has thought about it: the endpoint
  refuses unless `old_user_id` is orphaned, so a live admin's association cannot be moved. The
  docstring names the residual gap (no `previous_user_id` history to prove prior ownership); it
  is a known, bounded, documented limit rather than an unnoticed one.
- **Other `.or()` interpolations** (`api/groups/[id]/invites.ts:132,140,412`,
  `api/school/rate-compare.ts`, `api/_utils/orgPlatform.ts`). Values are group paths and id lists
  read from the database, not request input. Not reachable.
- **`api/admin/users.ts:299` `.ilike('email', '%${search}%')`.** The value goes through
  supabase-js as a URL-encoded parameter, not into an `or` expression, so a comma cannot add a
  filter. Worst case is an expensive scan.
- **The twelve service-role endpoints with no `verify*` import.** All read: `courses/*` and
  `courses/available` are public content; `board/snapshot/[code]` and `teacher/by-code` are
  deliberate capability-by-unguessability surfaces; `groups/*` authorise via
  `resolveGroupTreeCaller`/`callerCanSeeGroup`; `access/claim` verifies the token inline. No gap.

## Recommended order

1. **Finding 1** — one import, closes the predictable-secret half of the chain.
2. **Finding 2** — reuse the existing `possession_mint_attempts` throttle; closes the other half.
3. **Findings 3+4 together** — validate once at the `args` seam in `class-progress.ts`.
4. **Finding 5** — extract the already-triplicated `getClientIp` and prefer the attested source.
5. **Finding 6** — a decision about the compliance claim before it is a code change.

Each is small. None needs a schema change. Nothing here has been applied.
